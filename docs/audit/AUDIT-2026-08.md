# Adversarial audit — August 2026

Whole-codebase adversarial review of `apps/api`, `apps/mobile`, `packages/core`
and `packages/contracts` (~66k lines of source, ~54k of tests).

**Baseline at the time of audit — all green.** `pnpm test` 2843 passed / 300
skipped / 0 failed; `pnpm typecheck` clean; `pnpm lint` clean. Every finding
below is present in a tree where the whole suite passes. The 300 skips are the
database-backed suites: no `mongod` binary is reachable from this environment,
which is also why the three findings marked *(traced, not executed)* were
verified by reading rather than by running.

Each finding names a concrete failure — specific input or sequence, specific
wrong outcome, with `file:line`. Findings that were considered and refuted are
not listed.

---

## Severity summary

| | Count |
|---|---|
| Critical / High | 18 |
| Medium | 21 |
| Low | 11 |

The three areas carrying the most risk, in order:

1. **The withdrawal feature does not work at all.** Two independent bugs mean no
   withdrawal row reaches a farmer on any day, for any produce kind (H10, H11).
   This is the one area where being wrong is a regulatory event.
2. **Six separate paths lose or hide records** (H3–H8), all of them silent, and
   several of them permanent. The sweeper was built for one crash window; the
   mirror window and three of its neighbours are unhandled.
3. **Two cross-tenant paths** (H1, H2) — one a classic account pre-hijack, one a
   race between a token moving and a database moving.

## Critical and High

### H1 — Google sign-in hands an account to whoever registered the address first
`apps/api/src/routes/auth.ts:365`

`/auth/signup` never proves an address: `insertUser` (`auth.ts:274`) writes no
`emailVerifiedAt` and no mail is sent. Branch 2 of `/auth/google` then finds an
account **by email**, links the Google `sub` to it, marks it verified, and issues
a session for that account's org and role:

```ts
const byEmail = await findUserByEmail(identity.email);
if (byEmail) { ...
  await linkGoogleSub(byEmail._id, identity.googleSub);
  if (byEmail.emailVerifiedAt === undefined) await markEmailVerified(...);
  const pair = await startSession({ userId: byEmail._id, orgId: byEmail.orgId, role: byEmail.role }, ...)
```

Attacker signs up as `victim@example.com` — owner of their own org, unverified.
The victim later taps Sign in with Google and lands **inside the attacker's farm
as the attacker's user**. Everything they log syncs there; the attacker still
knows the password. It is also one-way: `/auth/signup` now 409s for that address
and no route unbinds a `googleSub`.

The token proves *the caller* controls the address. Nothing proves the *stored
row* ever did. This contradicts the project's own doctrine — `verification.ts:9`
("password signup accepts whatever is typed"), `identity.ts:76` ("Absent means
unproved"), and `/auth/forgot`, which already refuses to act on an unverified
address for exactly this reason.

**Fix.** Refuse the link when `byEmail.emailVerifiedAt === undefined`, keeping the
generic 401 so the route stays non-enumerating. Also refuse when `byEmail.googleSub`
is already set and different — `linkGoogleSub` is an unconditional `$set`, so an
address alone can currently rebind an account to a new Google identity, which is
the outcome `identity.ts:28` says the design exists to prevent.

*Fixed. Both conditions went into `linkGoogleSub`'s filter rather than into an
`if` above it — the reason `changeUnverifiedEmail` gives, and it also settles the
race between two first-time sign-ins for one address. The route returns the
disabled-account 401 verbatim. `tests/isolation/google-link.test.ts` covers the
guard at both levels, including that the two refusals are byte-identical.*

*What it cost: an account created by password — signup, invite, or join code —
has never proved its address, so the Google button refuses it until the address
is proved. A farm that only ever tapped Google would read that as the button
being broken.*

*That cost is paid off. `POST /auth/google/link` connects a Google account from
inside a session, which is a better proof than the address ever was and one the
sign-in route could not have had — so the step is gone rather than merely
signposted. It asks for the account password as well, exactly as `/auth/email`
does and for a sharper version of the same reason: a Google link is the one
grant here that nothing revokes, so a stolen session alone must not mint one.
The Account screen carries the control, and it names the Google address it
bound, because an Android chooser defaults to the top of two accounts and that
answer is the only moment a wrong one can be noticed.*

### H2 — Signing in to a different farm can write one farm's data into another's
`apps/mobile/src/auth/session.ts:233`

```ts
setAccessToken(pair.accessToken);          // farm B's token
await localStore().recordSessionEnd(null); // still farm L's store
```

The store moves later, in `Boot.onSignedIn` → `openLocalStore(orgId)`, which
closes a connection, opens a file and runs the migration ladder. **The engine loop
is not stopped across that gap** — `stopSync` has two call sites, `boot/start.ts:259`
and a dead one in `core/sync/session.ts:18`; neither `establish` nor
`Boot.onSignedIn` calls it.

Both tenant fences (`flush.ts:117`/`:127`, `pull.ts:75`/`:143`) compare
`storeGeneration()` to itself. They catch a store swap *during* a pass and are
blind to the token changing under a stable store. A tick in that window either
flushes the old farm's queue under the new farm's bearer token — the server takes
`orgId` from the token, so those records are created in the wrong org and come
back `applied`, so the original device never sends them anywhere again — or pulls
the new farm's snapshot into the old farm's SQLite file.

`tests/offline/farm-switch.test.ts` only moves the store mid-transport, which is
why this is uncovered.

**Fix.** Make the token and the store one transition: `stopSync()` before
`setAccessToken`, restart after `openLocalStore` resolves. Stronger: give
`setAccessToken` the token's `orgId` and have flush/pull refuse on a mismatch.

*Fixed, taking the second option. Stopping the loop across the transition
leaves the engine off if anything between the two calls throws, and there are
several sign-in paths to remember it in; a fence cannot be forgotten in one
branch. `setAccessToken` and `setLocalStore` each now carry the org they are
for, and `core/sync/tenant.ts` refuses a pass whose two halves name different
farms — in `flush` before the batch is sent and again before the answers are
written, and in `pull` before each page is asked for as well as after it
arrives.*

*A null org is unknown, not any, and never blocks: every device before its
first sign-in has a store and no token, and stalling those would be a worse
outage than the one being fixed. That makes the second argument droppable
without a failure, so both halves of the wiring are tested on their own —
`tests/unit/token-org.test.ts` and `tests/unit/store-org.test.ts` — beside the
fence tests in `tests/offline/farm-switch.test.ts`. All eight verified by
reverting the fix.*

### H3 — Cross-tenant `_id` collision on the projection insert *(traced, not executed)*
`apps/api/src/sync/apply.ts:487`

The mutation-log insert catches `E11000` and explains why (`apply.ts:202`:
*"_id is unique collection-wide, so a mutation id already used by another tenant
fails the insert rather than matching the org-guarded filter"*). The projection
insert has no such guard.

`restore.ts` re-enqueues a backup with its **original ULIDs** and justifies safety
with *"a `create` at a targetId that already exists is a `noop` in
`sync/projections.ts`"* — but `decideProjection` only sees the org-scoped
`existing`, which is `null` for another org. Lose a phone → fresh install mints
org B → restore → sign up → flush: `{_id:T, orgId:B}` collides with org A's
`{_id:T}`. Uncaught → 500 → the client retries forever; the row stays `pending`,
stalling the farm's pull feed; the hourly sweeper rethrows and, since
`listOrgIds()` sorts by `createdAt`, every farm created after it is never swept
again.

**Fix.** Wrap the insert in the same `E11000` guard the log write has, returning
`{kind: 'rejected'}` so the row is decided.

*Fixed as written, and the finding's "traced, not executed" is now closed:
`tests/isolation/sync-tenancy.test.ts` reaches it through the real route with
two farms and a shared `targetId`. Rejected rather than reported as a duplicate,
exactly as the log write decides it — saying `duplicate` would confirm to one
farm that another farm holds that id.*

### H4 — A crash between the projection and the outcome stamp is repaired as `noop`
`apps/api/src/sync/apply.ts:246`

The sweeper exists for the crash *between the log write and the projection*. The
mirror window is unhandled. Projection lands, `stampOutcome` does not → row stays
`pending`. On resend, `decideProjection` sees `existing !== null` → `{kind:'noop'}`
→ stamped as a **decided** outcome. `REPLICATES.noop === false`
(`outcome.ts:52`), so `readSnapshotPage` skips it and advances the watermark.

Device A has the record, the server has it, **device B never gets it — including
after a full `since=0` rehydration**. Identical for `delete`: the archive lands,
the stamp does not, and every other device keeps showing a record the farm deleted.

Confirmed untested: `crash-recovery.test.ts:32` states its fixture is *"the
envelope on disk, `outcome: pending`, no projection."*

**Fix.** Under repair, a `noop` must not be read as somebody else's change. Query
for another decided replicating row against the same `targetId`; if none exists,
this pending row produced the state, so stamp the replicating equivalent.

*Fixed, with the query narrowed to the state-producing outcome — `insert` for a
create, `archive` for a delete — rather than any decided replicating row. The
difference matters: a crash followed by an ordinary edit before the resend
leaves an `update` row against that target, and "any decided row" would read
that as somebody else having created it and leave the record on one phone.*

*A `delete` needs one more question, because its `noop` covers two worlds: the
record was already archived, and the record never existed at all. Only the first
converts — inventing an `archive` for a target nobody has would ship a removal
for a record no device holds.*

*Only the **log** is rewritten; the projection is not re-run. It already landed,
which is the premise — and it matters beyond tidiness, because archiving a photo
removes its bytes and a converted `archive` that re-ran the write would ask the
blob store to delete an object that is already gone.*

*Both repair paths go through it: the resend in `applyMutation`, and the
sweeper, every row of which is a repair by definition. Five tests in
`tests/sync/crash-recovery.test.ts` (CI), including the two `noop`s that must
stay `noop`.*

### H5 — An unreadable `pending` row freezes a farm's feed permanently
`apps/api/src/sync/sweep.ts:252` with `apps/api/src/sync/snapshot.ts:155`

`sweepOne` returns `{unreadable: 1}` **without stamping an outcome**.
`readSnapshotPage` *stops* (not skips) at any `pending` row and does not advance
`through`. A row whose payload no longer parses after a schema tightening is
therefore a permanent full stop for every device on that farm — while the client
is told `duplicate`, clears its outbox row, and reports itself up to date.

`outcome.ts:117` reasons that an unclassifiable row must not stall the feed. The
unreadable-*payload* case does precisely that.

**Fix.** Make "looked at, could not read" a decided-but-withheld outcome so the
feed can move past it, and re-sweep those rows on a later build.

*Fixed as written, both halves — the second of them only on the second
attempt. `unreadable` is a new `StoredOutcome`, deliberately not a
`ProjectionDecision`, because nothing was projected and nothing was refused; it
is the server failing to read its own record, and an operator should be able to
tell that from a refusal issued on purpose.*

*The first attempt shipped the re-offer half inert, and CI caught it.
`replayFromLog` asks a **third** question — may this row still be decided — and
answered it by testing for `pending` alone, so a row stamped `unreadable` was
selected by the sweeper's later pass and then walked straight past. Two of the
three questions had always agreed, which is why one function could answer all
of them; `isOpenToDecision` is the third written down, and
`tests/sync/outcome.test.ts` now pins all three side by side so the next one is
caught without a database.*

*The two halves pull opposite ways and both are needed, so the vocabulary
splits into two questions that used to have one answer. `isUndecided` stays
`pending` only, so the feed skips an unreadable row and advances past it.
`DECIDED_OUTCOMES` becomes `FINAL_OUTCOMES` and excludes it, so `stampOutcome`
will overwrite it — and the sweeper's query selects `pending` or `unreadable`,
so a build that can read the envelope is still offered the row. Including it
costs a pass nothing it was not already paying: these rows were `pending`
before, and consumed the same budget in the same order.*

*Five tests in `tests/sync/sweeper.test.ts` (CI) and three in
`tests/sync/outcome.test.ts` — including that the feed stops dead before the
sweep and reaches the record behind it after.*

### H6 — The projection repair sweeps on a `more: false` the server sends when it has merely stalled
`packages/core/src/sync/pull.ts:199` with `apps/api/src/sync/snapshot.ts:217`

Found independently by two reviewers, both reproducing it against the real store.

`runPull` treats `more === false` as proof the log ran out and calls
`finishProjectionRepair()`, which deletes every `records` row not stamped by this
replay and not named by a local outbox row. The server sets that same flag when
it stops at an undecided row — its own comment says *"`false` when stalled, though
there are certainly more rows on disk."* The client cannot tell the two apart.

The two comments contradict each other directly. `pull.ts:186` insists *"`more`
false is the whole condition, and it has to be"* and enumerates "the other two
ways a pass can end" — the server's stall is not among them.

Result: on any pre-repair device whose records arrived by pull, every record whose
log rows sit beyond the stall is deleted, and `repairDone` is set so the repair
never runs again.

**Fix.** Add an explicit `complete`/`stalled` flag to `PullResponse` and gate the
sweep on it.

*Fixed, but **not** that way — the suggested fix would have been worse than the
bug. `pullResponseSchema` is `.strict()` and ships inside every APK, so an added
key fails the parse on every handset already in the field and stops it hydrating
at all: the exact failure the note on `ENTITIES` in `contracts/mutation.ts`
describes, and issue #144 says farms are running builds as old as 0.1.7.*

*So the server stops lying instead: `more` is `stalled || hasMore`, one line, no
wire change, and it fixes every client version the moment the box deploys. The
round trip that answer costs is what was being optimised for, and it was the
wrong thing to optimise — the client asks once more, reads nothing, gets the
cursor back unchanged, and stops on its own no-progress guard with `more` still
true, so the repair stays open and finishes on a later pass.*

*A client-side gate was written and then reverted: making the sweep require
"the pass ended because the server said there was nothing left" sounds stricter
but breaks the legitimate empty-feed case, which exits by the no-progress guard
and not by the `more` branch — so the repair would never have completed on a
device with nothing to pull. Once the server is honest, `!outcome.more` is the
right condition, and `pull.ts` now carries a note saying why that line cannot
defend itself.*

*Two tests in `tests/sync/outcome.test.ts` — a stall says there is more and does
not move the cursor, an exhausted log says there is not. Both need mongod, so
they run in CI.*

### H7 — A corrupt-JSON row escapes quarantine and poisons the whole batch
`packages/core/src/db/sqlite-store.ts:83`

`readJson` returns `undefined` on a parse failure, and both row mappers put that
under a key declared `z.unknown()`. Verified against the pinned Zod:

```
key present, value undefined : true
key absent                   : false
JSON.stringify drops it      : {"id":"a"}
```

So `queuedMutationSchema.safeParse` **succeeds** on a row with corrupt payload
text and quarantine is never reached. `toEnvelope` copies the `undefined` through,
`JSON.stringify` drops the key, and the wire object has no `payload`. The server
parses the batch as a unit, so it answers 400 for the whole thing; the client's
`!isSyncResponse` branch eventually marks **every mutation in the batch — up to
100 good ones — rejected.**

The existing tests miss it because both corruption helpers also damage a *typed*
column, so the parse fails for the wrong reason (`tests/support/store.ts:129`
writes `value:'not json'` *and* `updatedAt:'not a number'`).

**Fix.** Make the parse failure representable — a sentinel or a `{ok, value}`
result — and treat it as unreadable before `safeParse`, so the row takes the
existing quarantine path.

*Fixed with the `{ok, value}` form. `readJson` keeps its lenient shape for the
two callers where unreadable genuinely means absent — `meta`, whose keys each
fall back to a default, and the pre-image in an update merge — and the row
mappers now return either a mapped object or the reason they cannot, so the
quarantine is reached before any schema is asked to vouch for the row.*

*The quarantined `raw` is the row as it sits on disk, corrupt column and all:
the mapped object would have the unreadable column silently missing, which is
what hid this in the first place. The projection half turned out to be the
worse one — `localRecordSchema.value` is `z.unknown()` too, so a record whose
stored value would not parse came back as a valid record with nothing in it and
was rendered as a blank animal rather than quarantined as a broken row.*

*The existing corruption helpers could not express this: `corruptRow` leaves a
valid payload and damages a typed column, `corruptRecordRow` damages the JSON
column and `updatedAt`. Two helpers that damage the JSON column and nothing
else are in `tests/support/store.ts`, and four tests in
`tests/offline/protections.test.ts` cover it — including that nothing reaches
the transport without a payload. All four verified by reverting the fix.*

### H8 — `attempts` is a lifetime counter, so one unreadable answer sweeps the batch to the inbox
`packages/core/src/sync/flush.ts:153`

`recordAttempt` increments the same column for a network failure, a 5xx and an
unreadable response, and it is never reset while a row is queued.
`rejectExhausted` matches on `attempts >= 6`, not on consecutive unreadable
answers. So the poison budget is normally spent on being offline, and the first
response that is not a parseable `SyncResponse` rejects up to 100 mutations at
once — e.g. a captive portal returning an HTML login page as a 200.

The 402 branch immediately above names this hazard — *"a farm running free for a
year would otherwise cross the ceiling and have its records swept into the inbox
six flushes in"* — and closes it for 401/402/426 only.

**Fix.** Count "the server refused to read this" separately from "we could not
reach the server", and reset `attempts` on any flush the server actually answered.

*Fixed on the first half, and deliberately not on the second. The ceiling now
ripens on `outbox_unreadable.answers` — the side table migration 8 added for
exactly this, until now inert — which counts only the answers the server
actually gave that left a mutation undecided: an unreadable body, or a
well-formed one that omitted it. Being unreachable no longer spends any of it,
which is the whole defect.*

*`attempts` is not reset, against the letter of the fix above. Once the ceiling
moved, resetting bought nothing and cost something: the migration's own comment
says `attempts` "goes on meaning 'times this has been tried', which is what a
diagnostic wants", and zeroing it would make a row that has been going nowhere
for a fortnight read as untouched on the diagnostics sheet.
`tests/offline/silent-server.test.ts` asserts that count directly and was the
thing that surfaced the trade-off.*

*The tally leaves with the mutation by whichever door it takes — cleared,
rejected, retried, or quarantined — and it is on the wipe list. Six tests, each
verified by reverting the fix, including a farm a fortnight offline meeting one
captive portal and keeping its work.*

### H9 — Update schemas inject `.default()` values, silently resetting untouched fields
`packages/contracts/src/clearing.ts:96`

`.partial()` makes keys optional but does not strip `.default()`, so a defaulted
field materialises in a payload the caller never sent:

```
task update      {}              ->  {"recurrence":"none"}
equipment update {name:"Kubota"} ->  {"name":"Kubota","hasHourMeter":true}
```

Traced end to end with the real schemas:

```
screen sends   : {"completedAt":null}
after Zod parse: {"recurrence":"none","completedAt":null}
server $set    : {"recurrence":"none"}
stored before  : {"title":"Check the water trough","recurrence":"weekly",...}
stored after   : {"title":"Check the water trough","recurrence":"none"}
```

Reachable at `JobsScreen.tsx:169` — the un-tick-a-job action, for a task with no
completion event, which is the legacy case the code's own comment says the `null`
was kept for. Un-ticking converts a weekly chore to a one-off; `taskDues` then
returns `[]` after its next completion and the job never appears again.

`equipment` shares the root cause but is not currently exploitable —
`EditMachineScreen.tsx:99` always sends `hasHourMeter`. Latent for any new field.

**Fix.** Unwrap `ZodDefault` before `.partial()` in `clearableShape`. Verified:

```
fixed {title:"x"}           -> {"title":"x"}
fixed {}                    -> {}
fixed {recurrence:"weekly"} -> {"recurrence":"weekly"}
fixed {recurrence:"yearly"} -> rejected
```

*Fixed as written, with the detection kept behavioural. `clearing.ts` already
argues that the probe must ask the field rather than inspect zod's class names,
"which change between major versions and would fail silently when they did" —
so `withoutDefault` identifies a defaulted field the same way `isOmittable`
identifies an optional one: it is the field that parses `undefined` into
something that is not `undefined`. Removal goes through the public
`removeDefault()`, and then **re-probes to confirm it worked**, throwing while
the schema is being built if a future zod moves that method. The alternative is
the bug quietly returning, which is what this whole class of failure looks
like.*

*The order inside `clearableShape` is load-bearing and commented: clearability
is decided from the original field, the default is stripped afterwards.
Deciding after the strip would make `z.string().optional().default('x')`
clearable and quietly reverse the rule the file exists to state.*

*Creates are untouched — they are built from the raw shape, so `task.recurrence`
still defaults on create, and a test asserts it. Four tests in
`tests/unit/clearing.test.ts`, verified red-then-green, including a property
walk over every mutable entity that mirrors the existing clearability walk: no
update schema may return a key its payload did not carry. `note` is the one
entity it skips, and the skip is asserted rather than assumed — its update is
hand-built with a required `body` and never goes through `updateSchemaOf`.*

### H10 — A withdrawal row can never appear on Today
`packages/contracts/src/due/notice.ts:26`

`urgencyOf` calls a row `later` unless `now >= at - noticeDays * DAY`. With
`withdrawal: 0` that reduces to `now >= at`. But `activeWithdrawals` drops a
withdrawal the instant `window.at <= now`. The row **exists** only while
`at > now` and is **visible** only when `now >= at`. Empty intersection.

Probed hourly across ±48h of a clear date through the real
`activeWithdrawals → withdrawalDue → todayList` chain:

```
clearsAt = 2025-05-20T00:00:00.000Z
hours sampled where the withdrawal EXISTS : 48
hours sampled where a row is ON TODAY     : 0
```

`tests/screens/today.test.tsx:98` claims to cover "it appears on the day the
withdrawal ENDS" while only asserting that nothing appears *during* the hold.

**Fix.** `withdrawal: 1`. Do **not** loosen `activeWithdrawals` — that boundary is
exclusive on purpose and widening it would clear produce a day early.

### H11 — Milk and meat withdrawals are never built at all
`apps/mobile/src/hooks/useDues.ts:118`

`useDues` only ever calls `withdrawalsBySubject('egg', ...)`. `WITHDRAWAL_KINDS`
is `['egg','meat','milk']` and `withdrawalDue` handles any kind. A dairy goat's
milk withdrawal produces no Today row; meat holds appear nowhere at all. Only
`ProduceScreen` shows milk holds, for one group at a time.

Together with H10: **no withdrawal reaches a farmer on any day, for any produce
kind.** This is the poultry-only assumption `CLAUDE.md` forbids, in the one place
where being wrong is a regulatory event.

### H12 — Weekly trend buckets read zero across a DST boundary
`packages/core/src/read/trend.ts:75`

`bucketsBack()` walks back by a literal `7 * 86_400_000` ms while `bucketStart()`
keys buckets at *local* midnight. Once the walk crosses a DST transition every
older bucket is offset by an hour and can never match a record's key, so
`totals.get(key)` misses and the week renders as 0. Reproduced — 6-week chart
ending 24 Mar 2025, `America/New_York`:

```
MISS  bucket=Sun, Feb 16, 11:00 PM   log lands in Mon, Feb 17, 12:00 AM
MISS  bucket=Sun, Feb 23, 11:00 PM   log lands in Mon, Feb 24, 12:00 AM
MISS  bucket=Sun, Mar  2, 11:00 PM   log lands in Mon, Mar  3, 12:00 AM
ok    Mar 10 / Mar 17 / Mar 24
3 of 6 buckets can never be matched -> those weeks render as 0.
```

Affects `eggTrend`, `produceTrend`, `feedTrend` and `feedSpend`; `direction()`
then reports a fabricated collapse. The rest of the codebase gets this right —
`frost.ts` documents avoiding exactly this, and `history.ts`, `groups.ts` and
`weather.ts` all use `setHours(0,0,0,0)` on the date in question.

### H13 — Every harvest is filed under its planting's season, not the year it happened
`packages/core/src/read/numbers.ts:143`

`readNumbers` buckets by `plantingById.get(harvest.plantingId).season` and ignores
`harvest.occurredAt`. `season` is stamped at planting creation and never moves, so
any crop whose picks fall outside the planting year is attributed to the wrong
year:

| record | reality | screen says |
|---|---|---|
| Rhubarb crown season 2024; 8 kg picked May 2026 | 8 kg in 2026 | 2026: **0 kg, 0 picks** |
| Garlic sown Oct 2025; 3 kg lifted July 2026 | 3 kg in 2026 | filed under **2025** |

These are first-class shapes in the bundled library — `crops.ts:98` has garlic as
autumn-sown, and asparagus / rhubarb / raspberry / blueberry / strawberry are all
perennials. `farm-numbers.ts:36` asserts the opposite of the observed behaviour:
*"it buckets by the year of `occurredAt`. **The two agree**, which is the point."*
They do not. Every other column on that screen buckets by `occurredAt`.

`tests/unit/numbers.test.ts:112` locks the wrong behaviour in.

### H14 — Removing a photo destroys the bytes and swallows the failed write
`apps/mobile/src/components/Photos.tsx:135`

`forgetBytes(photo.id)` deletes the file, then `void log({op:'delete'})` fires with
no `await` and no `catch`. On a full disk — the reason someone is deleting photos
— the JPEG is gone, `enqueue` throws `StorageFullError` unhandled, and the panel
closes as if it worked. For a photo with no `uploadedAt` that was the only copy:
`BACKUP_EXCLUDES` means the backup file does not carry bytes. The record stays
live with `uploadedAt` absent, which in `sync/photos.ts:141` matches neither the
upload nor the download branch, so it can never get bytes on any device again.

The sibling path in the same component does it correctly (`add()` try/catches into
`setProblem`), and `<Failure>` is already mounted and unused by `remove`.

### H15 — `processingDue` is a permanent resident
`packages/contracts/src/due/growout.ts:118`

Every other builder disappears because a record appeared. `processingDue` reads
only fields of the group itself, so nothing a farmer *does* clears it. A meat
flock goes `overdue` a day after the window opens, sorts **first** on Today
(`URGENCY_ORDER.overdue = 0`) in the alert tint, and stays there forever —
processing the birds and recording the cull changes nothing. The only escapes are
lying about the group or archiving it.

This is the exact failure `due/types.ts:236` builds every other builder against.

### H16 — The CSV service sheet reads a field nothing writes any more
`packages/core/src/export/csv.ts:430`

`ServiceDoneScreen` writes a `serviceCompletion` and never touches `maintenance`.
`read/iron.ts:219` and `read/history.ts:457` were both updated to resolve the
completion; `csv.ts` still reads raw `maintenance.lastDoneAtDate`. Export
"everything" → `Last done` and `At hours` blank on every row. Export "the last
year" → `at: v.lastDoneAtDate ?? 0` puts every row at the epoch, `within()` drops
them all, and `ExportScreen` throws *"Nothing in services for that period."*
There is no `serviceCompletion` sheet either.

### H17 — The freezing-night birth warning never fires for an overdue birth
`packages/contracts/src/warnings.ts:554`

```ts
birth.at >= today && birth.at <= today + BIRTH_WINDOW_DAYS * DAY_MS
```

`birthDue` only emits a row while `bornAt` is unrecorded, so `at` in the past means
*she has not kidded yet and nobody logged it* — the routine case, since
`GESTATION_DAYS`' own comment says these "vary by several days… The date is when
to be ready, not a promise." A doe two days past her date on a −7 °C night gets no
`birth-cold` warning. The code comment justifies only the upper bound.

### H18 — History produce rows print raw storage units
`packages/core/src/read/history.ts:346`

The `productionLog` builder interpolates the stored value and unit verbatim while
`summarise` converts the identical quantity into the farm's system. On an imperial
farm:

```
1 gal · 7.5 lb · …          <- day summary
  3785 ml milk — The goats  <- the row inside it
```

`units.ts:298` documents `formatProduce` as existing for exactly this failure. The
row is also the accessibility label, so it is read aloud as "3785 ml".

## Medium

- **M1** `DELETE /members/:id` never calls `revokeAllForUser`, and `requireClaims`
  never checks `disabledAt` — so a removed member keeps `GET /snapshot` (a whole-farm
  export) and `GET /photos/:id` until the access token expires. `identity.ts:556`
  claims the opposite: *"access ends immediately."*
- **M2** The sweeper has no error containment per row or per farm — the only `try`
  is the timer at `sweep.ts:472`, so one throwing row abandons the pass for every
  remaining farm.
- **M3** `retryRejected` (`sqlite-store.ts:706`) reuses the mutation id, which is the
  server's idempotency key, so any refusal decided *after* the envelope was logged
  replays to `decidedResult` forever. "Send it again" can never work for the low
  hour-meter reading or the archived-record conflict — the two refusals whose
  messages tell the farmer to retry.
- **M4** `restoreBefore` (`sqlite-store.ts:432`) skips the restore when `updatedAt`
  moved, but a pulled *update* merges and moves it without touching the refused
  field — and the pre-image is deleted unconditionally first. Discarding a refused
  edit then leaves a value no other device has, permanently.
- **M5** `shearingWarnings` (`warnings.ts:594`) has the same lower bound as H17;
  reproduced, a clip 3 days overdue raises no wet-weather warning while one due in
  5 days does.
- **M6** `forgetWeather()` is called only from tests (11 sites, all under `tests/`).
  Move the farm's pin and another county's alerts show as live for 15 min, and
  offline the old grid's forecast persists for `FORECAST_STALE_MS` = 48 h — driving
  frost, freeze and heat warnings for the farm's stock.
- **M7** `markSynced` is called only from `flush.ts:270`, after *outgoing* mutations.
  A pull never sets it, so a phone that installed → signed in → pulled 1,500 records
  is told *"1,500 records, on this phone only — nothing has been copied anywhere
  else"*, and advised to set up the account it already has.
- **M8** `POST /support` has no raised `bodyLimit` (only the photos scope does) and
  Caddy sets no `request_body max_size`, but the contract allows
  `records: z.string().max(20_000_000)`. Anything over 1 MiB is a 413, the ticket
  has no attempt cap, and the lean bundle is lost with it.
- **M9** `Timeline.tsx:184` deletes `event.entity` by `event.id` on the premise
  *"Every entity a history row can be built from is append-only"* — false for `task`
  and `maintenance`, whose legacy builders set `id` to the schedule's own id. One tap
  archives the oil-change schedule.
- **M10** `FeedScreen.tsx:445`, `ProduceScreen.tsx:166` and `HarvestScreen.tsx:201`
  hand `Tally` a callback that swallows the promise, so its restore-on-rejection never
  fires and a failed write resets the count and prints a confirmation.
- **M11** `projectReading` clamps to `now` when the meter is past target and `useDues`
  recaptures `now` each pass, so an hours-based service can never reach `overdue`. A
  tractor 650 hours late reads "today". `tests/unit/due.test.ts:198` asserts `'now'`
  for exactly this machine.
- **M12** `DueRow.tsx:43` measures elapsed hours from *this instant* against
  midnight-anchored dates, so a job due today reads "Due yesterday" from 13:00 — the
  failure the comment two lines above claims to prevent. Untested.
- **M13** `SiteSetupScreen.tsx:140` omits the zone key when blank instead of sending
  `null`, so the field cannot be cleared and stale hardiness warnings persist.
- **M14** `TreatmentScreen.tsx:155` stamps `administeredAt = Date.now()` on a create,
  and `withdrawalWindow` takes `Math.max(administeredAt, treatmentEndsAt)` — so a
  back-dated last dose is discarded. Errs long (safe for food safety) but costs the
  farm sellable produce and writes a false administration date.
- **M15** 15 varieties ship twice with conflicting agronomy —
  `corn-golden-bantam` (78 days) vs `sweet-corn-golden-bantam` (80),
  `bean-provider` (spacing 3) vs `bush-bean-provider` (4),
  `pepper-jalapeno` (transplant +3wk) vs `pepper-jalape-o` (+2). The merge dedupes by
  `id`, but 24 hand-tuned ids do not follow the generated slug rule and the slug strips
  non-ASCII. `library.test.ts:47` passes precisely because the ids differ.
- **M16** `farm-numbers.ts:268` counts service *schedules with a recent date* rather
  than completions, so each schedule contributes at most 1 — and `hadOne` uses the same
  field, so a machinery-only farm can lose its entire previous-year column.
- **M17** No `breeding` builder in `history.ts`, so a kidding, lambing or calving
  produces zero rows — while `incubation.hatchedAt` (the poultry equivalent) has one.
  `AnimalScreen` renders "What happened to her" and her giving birth is not in it.
- **M18** `storageDue` is exported, tested and never called. `useDues.ts:44` claims
  *"Every builder the contracts package ships is wired in here"*; it is not, and there
  is no data source for it either.
- **M19** `rotateSession` (`refresh.ts:174`) reads a lost `consumeRefreshToken` as
  "another exchange won the race", but the filter also matches on `revokedAt` — so a
  revocation landing inside the window is swallowed and a fresh 90-day token is issued
  into a family that was just revoked.
- **M20** `backupEntrySchema.entity` is the strict enum while widening the entity list
  deliberately bumps neither version gate, so a farm's own backup from a newer build is
  refused with *"That file is not a backup from Evenglow."* `pullResponseSchema` got the
  forward-compatibility fix; backup did not.
- **M21** `careApplies` treats "no default interval" as "anatomically impossible" for
  `hoof-trim` and `dental`, and `OTHER` sets both `null` — so pigs, rabbits and every
  unlisted species are told they have neither feet nor teeth, with no way to switch the
  chips on.

## Low

- **L1** `warnings.ts:313` uses `day.day <= today + DAY_MS` against local-midnight keys,
  so on the DST fall-back night (25 h) tomorrow's warnings are dropped entirely — frost,
  freeze, heat, birth-cold and shearing-wet. Reproduced for 2 Nov 2025, `America/New_York`.
- **L2** `csv.ts:313` uses `named(groupName, v.flockId)` for treatments, so every
  per-animal treatment exports with a blank subject. The four sibling sheets handle both.
- **L3** `hash64` (`support.ts:157`) is effectively 32-bit: both lanes share seed and
  prime, and `high ^= (code >>> 8) & 0xff` is always zero for ASCII. 2000 distinct
  same-length inputs produce **1** distinct high prefix.
- **L4** `tick` has no re-entrancy guard and `transferPhotos` has no single-flight, so a
  `nudge()` mid-tick can upload the same photos twice.
- **L5** `markSynced` and `setSyncHeld(null)` in `applyResults` sit past the last
  farm-switch generation check.
- **L6** `PUT /photos/:id` raises the body limit to 3 MB, has no rate limiter on its
  scope, and authenticates inside the handler — after the body is parsed.
- **L7** `POST /billing/play` has no limiter and spends an RSA sign plus two Google
  round trips per request; the sibling notification route got 60/min for exactly this.
- **L8** `boardPolicy` emits `style-src 'nonce-…'`, which does not authorise the six
  inline `style=` attributes in `ops/page.ts`; the board's own layout is stripped.
- **L9** `plural` defaults to `${one}s`, so a day with two losses summarises as
  "2 losss". The interface doc four lines above states the intended output.
- **L10** `start()` returns early on the no-account path before `startTriggers()`, and
  `Boot.onSignedIn` only calls `startSync()` — so after the ordinary first sign-in,
  `AppState` and `expo-network` go unlistened for the life of the process.
- **L11** `ServiceDoneScreen.tsx:136` composes `${line} — ${machine.name}` (up to 163
  chars) against a 120-char cap, after the `serviceCompletion` is already durable — so
  the raised job is lost and a re-press writes a second completion.

## Notes on method

- Twelve parallel reviewers, one per area, each instructed to refute its own findings
  before reporting. Every finding above was then re-verified against source by hand;
  findings that did not survive are not listed.
- Where two reviewers disagreed, the disagreement is resolved in the text. H17 is the
  one case: one reviewer argued a past due date means the birth already happened. That
  is wrong — the due row's existence is proof it was not recorded.
- Empirical reproductions (DST buckets, the withdrawal-visibility probe, the Zod
  `unknown` behaviour, the default-injection chain, the variety conflicts, the DST
  warning drop) were run against the repository's own code.
- H3, H4 and H5 are traced rather than executed: no `mongod` is reachable here. They
  should be reproduced against a live database before their fixes are written.
